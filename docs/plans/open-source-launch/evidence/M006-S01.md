**Seen red first.** The contract failed all eleven cases with no workflow.
Two later failures were the contract's own: a report-name pattern that
rejected the digit in `windows-x64`, and a measurement check that matched a
heading string quoting `spctl --assess` instead of the invocation; both
were corrected in the contract, and the workflow was not changed to suit

**What the verifier does**, on `workflow_dispatch` with a tag and on every
published Release, with `contents: read` and nothing more. Per platform, on
a fresh hosted runner: `gh release download` fetches the tag's zip and
`SHA256SUMS` as a stranger would; the digest is checked (`shasum -a 256 -c`
on macOS, `sha256sum -c` on Windows) and the provenance attestation verified
with `gh attestation verify --owner JimAKennedy`. macOS then applies the
quarantine attribute a browser download carries, extracts, installs into
`~/Library/Audio/Plug-Ins/VST3`, records `xattr -l`, `codesign -dv` and
`spctl --assess` on the quarantined bundle, clears the attribute with the
README's own `xattr -dr` command and records the verdict again. Windows
writes the Mark-of-the-Web the browser would, extracts, installs into
`%LOCALAPPDATA%\Programs\Common\VST3`, and records the `Zone.Identifier`
stream on the zip and on the installed binary and its
`Get-AuthenticodeSignature` status. Both then run pluginval 1.0.4,
digest-verified as in `ci.yml`, at strictness 8 against the installed
bundle, and upload a per-platform report. The verdict commands are
measurements and cannot fail the job; the download, the digest, the
attestation and pluginval can.

**The proof it does that** is task 3's run against `v0.2.0-rc.1`; no row
closes here.

### What a clean machine measured (OS33)

**macOS 14.8.9 (arm64), fresh `macos-14` runner.** The zip's digest matched
`SHA256SUMS` and the provenance attestation verified. With the quarantine
attribute a browser download carries (`com.apple.quarantine: 0083;…;Safari;`)
applied to the installed bundle, `codesign -dv` reported
`Signature=adhoc`, `flags=0x20002(adhoc,linker-signed)`,
`TeamIdentifier=not set` — the linker's ad-hoc signature, not a Developer
ID — and `spctl --assess --type execute` said **`rejected`, `source=no
usable signature`**. After `xattr -dr com.apple.quarantine`, the README's
instruction, the attribute was gone and `spctl` still said `rejected, no
usable signature`: Gatekeeper's verdict is about the signature, and the
quarantine attribute decides only whether the verdict is consulted when a
user opens the download. pluginval 1.0.4 at strictness 8 then loaded the
installed bundle and finished `SUCCESS`.

**Windows Server 2022 (10.0.20348), fresh `windows-2022` runner.** Digest
and attestation verified. The zip carried the Mark-of-the-Web a browser
writes (`ZoneId=3`); `Expand-Archive` did **not** propagate it to the
installed binary (`no Zone.Identifier stream`). `Get-AuthenticodeSignature`
on `Contents\x86_64-win\poly_plugin.vst3` reported **`NotSigned`**.
pluginval 1.0.4 at strictness 8 loaded the installed bundle and finished
`SUCCESS`.

### What the first cut broke, as rows or issues

- **The verifier's `release: published` trigger never fires** for our
  Releases: `release.yml` publishes with the workflow's own `GITHUB_TOKEN`,
  and GitHub runs no workflow for an event that token caused; only the
  dispatched run existed. Filed as
  [#348](https://github.com/JimAKennedy/poly/issues/348).
- **The report does not show whether clearing the quarantine is what makes
  the plugin load**: pluginval ran only after the clear. A second pluginval
  pass with the attribute still set would say whether the README's
  instruction is necessary or merely sufficient. Filed as
  [#349](https://github.com/JimAKennedy/poly/issues/349) rather than a row:
  it is a measurement to add, not a defect in what ships.
