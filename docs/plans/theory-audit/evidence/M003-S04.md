**F31's claim was checked against the engine, not taken from the ledger.**
`applyTimingShifts` in `engine/src/engine.cpp` applies swing, then the
syncopation offset, then `cfg.microTimingMs[cycleStep]`, and finally derives
`jitterPpq` from `deterministicRand(...)`. Humanize is therefore seeded and
reproducible for a given patch and seed, but carries no per-position structure —
which is precisely the structure Polak's stable short-medium-long profile has.
Had the claim not held, the disclosure would have been the wrong disclosure.

That reading also produced **B10**. The same function shows `microTimingMs` is a
per-step array, and `web_ui_view.cpp` handles a `setMicroTiming` action clamped
to ±20 ms which `ui.js` renders as the micro-timing bars. So the step's "until
Poly ships subdivision-profile support" was not merely vague, it was inaccurate:
the mechanism exists and the missing piece is measured data. B10 is the first
`B` row outside M006, tracked separately so the feature-claim correction is
visible rather than folded into a disclosure about something else.

Rule 8 was deliberately not edited. It states what the scholarship found; the
contrast belongs where Humanize is actually named, which is construction step 5.

The step keeps its practical advice and adds the distinction in the terms a
reader can act on: jitter reproduces the *presence* of non-isochrony and not its
shape, a straight grid plus noise is still not the feel, and per-step
micro-timing is where a profile would go. It stops short of claiming Poly can
reproduce Polak's profile, because it cannot — no measured profile is supplied.

The `S04-F31` present arm asserts `systematic profile`, not bare `systematic`:
the page already contained "systematically", and `containsClaim` matches
substrings after normalisation, so the looser arm would have passed before the
edit. This is the third pre-satisfied arm caught by checking during planning in
this milestone.
