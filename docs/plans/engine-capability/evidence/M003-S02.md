## M003/S02 — task 1: a lane's steps can be grouped into cells

- `format` → exit 0
- `unit` → exit 0, 618 tests, 0 failures
- `engine-isolation` → exit 0, 495 tests, 0 failures

Written test-first; the four cases failed to compile because neither the fields
nor `swingCellFor` existed.

This is the gap S01's design named and did not close. `cellCount > 0` collapses
a lane to one step per cell, so a `{2,2,3}` davul has three steps and nothing
inside a cell to swing. `swingCellCount`/`swingCellSizes` group a lane's
*existing* steps instead: seven steps, three cells, 2+2+3.

The helper returns an invalid result rather than a guess in three cases — no
grouping declared, sizes that do not account for exactly the cycle's steps, and
a step out of range. Each has a case, because a grouping that does not add up is
a configuration error and reading past the end of a 64-int array is the
alternative.

**The size guard fired again**, and was answered with a measurement rather than
a new constant: `GrooveState` 15888 → 17936, and the three-copy pipeline at
**0.68 µs/block, still 0.02% of a 128-sample block period**. Across M003 the
struct is up about 30% and the copy about 50%, unchanged as a share of the
budget. Recorded because two slices adding 30% is obvious in aggregate and
invisible one commit at a time.

The alternative — reusing `cellSizes` for the grouping when `cellCount == 0` —
would save 2 KB and give one field two meanings depending on another. That is
what this milestone already rejected when it gave the profile explicit
precedence over `cellSizes` rather than combining them.
