`ThreeCopyPipelineFitsBlockBudget` passes.

The first test run failed at a `1e-9` tolerance because `1.1f / 0.9f` differs
from the double ratio by about 6e-8. The engine was right and the test was
wrong: the profile is stored as `float` by design, so a tolerance tighter than
float precision tests the storage type rather than the arithmetic.

## M003/S01 — task 2: wired through `prepareLaneContext`

- `format` → exit 0
- `unit` → exit 0, 612 tests, 0 failures
- `engine-isolation` → exit 0, 489 tests, 0 failures
- `rt-safety` → exit 0

**All three new cases passed on their first run, which proves nothing**, so each
was mutated against: a probe discarding the profile in `prepareLaneContext`.
The first run of that probe is the finding:

| Case | Under the probe |
|---|---|
| differs from the even grid and the swung grid | **failed** |
| holds its ratios across tempi | *passed* — vacuous |
| does not lengthen the cycle | *passed* — vacuous |

An even grid also holds its ratios across tempi, and also does not lengthen the
cycle, so two of the three cases could not fail. Both were strengthened to pin
that the intervals are uneven before asserting anything about them, and the
probe re-run: **all three fail with the profile ignored, all three pass with it
honoured.** This is the M007 finding recurring in new code — a predicate that
cannot fail reads exactly like one that passes — and it took a mutation round to
see, not a reading of the test.

**A bound was wrong, and the test written for it does not catch it.** On the
profile path `cfg.cellSizes[c]` is unset, so `maxStepDur` stayed at the base
step while a profiled step can be 1.1× longer, under-covering the lookahead by
about 0.0008 PPQ. `SplitRenderingMatchesWholeRendering` — nineteen split points
across the cycle — **passes both before and after the fix**, because the
additive path enumerates whole cycles with a one-cycle margin that swamps the
shortfall. The bound is now derived from `cumPpq`, which is correct on both
paths. The fix is correctness of the bound, not a demonstrated bug, and the test
is a regression guard rather than a proof; saying otherwise would be claiming a
mutation proof that was not obtained.

## M003/S01 — task 3: state version 19 → 20

- `format` → exit 0
- `unit` → exit 0, 614 tests, 0 failures
- `engine-isolation` → exit 0, 491 tests, 0 failures

Follows `kKotekanModeStateVersion` exactly — the most recent precedent, in the
same file. `profileCount` is written first and only that many floats follow, so
a lane with no profile costs four bytes rather than 260. The reader rejects a
count outside `[0, kMaxSteps]` rather than trusting it, because a forged count
would otherwise walk it off the end of the array.

Both cases were written after the implementation, so each was mutated against,
and the two probes are complementary:

| Probe | Result |
|---|---|
| write side never emits the profile | `SubdivisionProfileRoundTrips` **fails**; the pre-v20 case passes |
| read guard lowered to `>= 19` | `PreV20StateDefaultsToTheEvenGrid` **fails**; the round-trip passes |

Each probe kills exactly one case, which is the evidence they test different
things rather than the same thing twice.

**A stale build reported a false red.** After restoring the second probe, the
suite still showed `PreV20StateDefaultsToTheEvenGrid` failing against sources
that were provably correct — `git diff` showed the guard back in place. The
header change had not been recompiled; `touch`ing the headers and rebuilding
turned it green. The hazard runs both ways, and the dangerous direction is the
other one: a probe that *should* have failed reading as passed. Every mutation
result in this slice was taken from a build that had just compiled the edit.
