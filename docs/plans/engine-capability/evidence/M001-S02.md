## M001/S02 — task 1: `Cuban Son Montuno`'s clave lane

- `format` → exit 0 (clang-format reformatted the new C++ on first run; the
  build and unit suite were re-run after it, not just re-formatted)
- `unit` → exit 0, 590 tests, 0 failures
- `engine-isolation` → exit 0, 467 tests, 0 failures
- `site-unit` → exit 0, 275 tests, 0 failures
- `doc-conformance` → exit 0, 254 tests, 0 failures

The failing test named the defect exactly. Before the fix the clave lane's
onsets were `{ 0, 3, 6, 9, 12 }` — `E(5,16)`, baked by `lockReferentLane` —
against the son clave's `{ 0, 3, 6, 10, 12 }`. That is the one-pulse difference
at the ponche which Chapter 3 describes, measured rather than asserted.

The test looks the preset up by name rather than by index, because tasks 2 and 3
insert presets and every later index would shift; a test pinning an index would
silently start checking a different preset. The Euclidean comparison is computed
from the lane's own hit count, cycle and rotation, so the test states the
relationship rather than asserting two hand-typed arrays.

`lockPresetReferent` leaving the lane alone is proved by the same assertion: the
test reads the preset through `makeFactoryPreset`, so a re-bake would have
restored the Euclidean pattern and failed it.

**`presets.json` did not change, and cannot.** The emitter carries `timeline`
and `fixedPatternLength` but not the pattern itself, so the generated file
cannot distinguish an exact clave from a Euclidean bake. The plan's step
expecting the lane's data to change was wrong; the correct outcome is that the
file is byte-identical. Noted for the milestone report — the site consumes this
file, so nothing rendered from it can show the true pattern.

## M001/S02 — task 2: the `Rumba Clave` preset

- `format` → exit 0
- `unit` → exit 0, 591 tests, 0 failures
- `engine-isolation` → exit 0, 468 tests, 0 failures
- `site-unit` → exit 0, 275 tests, 0 failures
- `doc-conformance` → exit 0, 254 tests, 0 failures
- `doc-discipline` → exit 0, `count-drift: no hardcoded inventory counts`

Guaguancó texture on the exact rumba clave — onsets 0, 3, 7, 10, 12, gaps
3-4-3-2-4, with the third stroke on 7 where the son clave puts it on 6. The
quinto alone carries mutation, because it is the free voice in rumba.

**No `kWebPresetLaneNames` row was added, deliberately.** The array is declared
to `kFactoryPresetCount` but initialised sparsely — 14 rows — and every preset
from index 14 on falls back to default lane names through the null guard at the
`applyPreset` call site. Appending a row would have given it index 14 and
relabelled `makeEweAgbekor`'s lanes. The `static_assert` pins the array's
extent, not its row count, so it cannot catch an omission; the plan said
otherwise and was corrected.

**The generator ran a stale emitter and silently wrote 43 presets.**
`site/scripts/generate-presets-json.mjs` returns early whenever the emitter
binary exists and only builds it when missing, so a change to `presets.cpp`
does not rebuild it. The file's own header calls a stale `presets.json` "a
silent correctness bug we already paid for". Worked around here by building
`poly_presets_emit` explicitly before regenerating. Worth an issue; not this
slice's to fix.

Two site cases caught consequences worth keeping:

- `presets.json — schema shape` pinned the count at 43; updated to 44.
- the `preferredRoles` snapshot rejected `68:agogo`. That was a real mistake
  rather than a snapshot to widen: note 68 is a bell, and the quinto is the
  highest of the three congas. The quinto moved to 63 (open high conga) and the
  salidor from 36 (a bass drum) to 64 (low conga), which is what the guaguancó
  trio actually is.
