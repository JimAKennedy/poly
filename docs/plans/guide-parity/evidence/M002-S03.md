**The weight redistributes rather than adds, and the render case is why.** The
first implementation ran from `1.0` at the cycle's start to `1 + shape` at its
end — only ever raising the probability. The render case measured **exactly 1800
early against 1800 late, with and without a shape**: once fills saturate, a
weight that can only raise cannot shift anything. It now runs from `1 - shape`
to `1 + shape`, so early fills become rarer as late ones become commoner, which
is also the truer musical claim.

**The render case found a second defect in its own setup.** The identical-1800
figure persisted after the redistribution fix, and the cause was the test:
`fillEveryNBars` makes `if (isFillBar) return StepOutcome::Add;` fire *before*
the roll, so every step became an unconditional Add and the weighted
probability was never consulted. The weight applies to the probabilistic path,
driven by a `FillLikelihood` envelope. The test now drives that, and the comment
records why — the wrong path is an easy mistake to repeat.

**Probed, with the render case added first this time.** S02 established that
unit cases on the helper cannot see the wiring, so the order was inverted here:

| Case | Under the probe (phrase weight discarded) |
|---|---|
| neutral when unset | passes |
| rises monotonically toward the boundary | passes |
| shape controls concentration | passes |
| ungated lane does not divide by zero | passes |
| **render: fills concentrate toward the boundary** | **fails** |

**A stale build, again.** After restoring the probe the suite still reported the

rebuild turned it green. That is the third occurrence this session and the

## M002/S03 — task 2: a tihai lands on the target

- `format` → exit 0
- `unit` → exit 0, 669 tests, 0 failures

`solveTihai(phraseLength, remaining)` solves `3P + 2g = remaining` for the gap.
That is the whole of the arithmetic `06-indian-classical` asks the reader to do
by hand, and it is pure — no engine state, no transport — so it is testable
directly and reusable wherever the figure is constructed. The row allowed it
engine-side or UI-side; engine-side keeps it testable without a browser.

The property case asserts the third repetition lands exactly on the target
across sixteen `(phrase, remaining)` combinations, rather than checking the
guide's one worked example and stopping.

**The unsolvable case is the one that matters,** and it is mutation-proved:
removing the negative-gap guard makes `ReportsUnsolvableRatherThanOverrunningTheTarget`
fail while the other three stay green. A phrase too long for the space has no
tihai, and returning one anyway would place the third repetition *past* the
target — landing after sam, which is the one thing the figure must never do.
Silently rounding would hide exactly that.
