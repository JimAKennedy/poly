## M005/S01 — task 3: what stopped TSan reporting on 2026-08-17

**Answered. It was a real fix, not a narrowing — and that makes the remaining
question sharper, not softer.**

The cheap eliminations first, by reading rather than building:

| Candidate | Changed in the window? |
|---|---|
| `.github/workflows/sanitizers.yml` — filter or target | **no** |
| `tests/host/host_tests.cpp` | yes, +158 lines |
| `plugin/source/` handshake implementation | yes, 21 files |

`plugin/source/processor.h` carries the answer in its own comment. Commit
`076f545` replaced the host→RT exchange with a lockless **triple buffer**, and
names the defect it was fixing:

> the prior design used two slots and an alternating writer index … after the
> reader's `exchange(-1)` the writer had NO way to know the reader was still
> copying `slots[cur]`, so the writer's second alternation could write
> `slots[cur]` concurrently with the reader's detach copy (**TSan data race on
> the `slots[]` detach copy, all five hot slots** — pinned in M031 S01 T01). Two
> slots are fundamentally insufficient …

That lands on 2026-08-16, which is exactly when the 22-night streak stopped. The
TSan data race was diagnosed and fixed by other work, before this milestone
existed. Nothing was suppressed and no window was narrowed.

**What that leaves is the harder finding.** The handshake has been stable since:

| File | Last changed |
|---|---|
| `plugin/source/processor.h` | 2026-08-16 |
| `tests/host/host_tests.cpp` | 2026-08-17 |

A month later, on 2026-09-16, `HandshakeStress_NoTearNoLoss` still caught a torn
read — its own assertion at `host_tests.cpp:1307`, in a build where ASan
reported no memory error. So the 09-16 occurrence is **not** the race that
076f545 fixed. It is either a residual tear the triple buffer does not close, or
a defect in the test's own invariant.

That distinction is M005/S02's subject, and it is a better-posed question than
the one this milestone started with.

## M005/S01 — task 4: classification and close-out

The definition of done asks for every filed occurrence classified by sanitizer,
stack and date. There are 23 nightly failures behind #142's 22 comments, and
they fall into exactly two groups.

### Group A — 22 occurrences, 2026-07-26 → 2026-08-16, `TSAN-PLUGIN`

- **Sanitizer:** ThreadSanitizer, plugin build.
- **Report:** `WARNING: ThreadSanitizer: data race`,
  `SUMMARY: ThreadSanitizer: data race … in memcpy`.
- **Stack:** `tests/host/host_tests.cpp` at 1069, 1104, 1132, 1139
  (run `31924034914`, 2026-08-16).
- **Test:** `HostTests.HandshakeStress_NoTearNoLoss`.
- **Status: already fixed.** Commit `076f545` (2026-08-16) replaced the two-slot
  host→RT exchange with a lockless triple buffer, naming this exact race in
  `processor.h`. The streak stopped the same day. Nothing suppressed —
  `.github/tsan.supp` contains no entries.

### Group B — 1 occurrence, 2026-09-16, `ASAN-PLUGIN`

- **Sanitizer:** AddressSanitizer, plugin build — **which reported nothing.**
  No memory error, no leak. The job failed on the test's own assertion.
- **Report:** `host_tests.cpp:1307` —
  `torn-read: final noteMap[1]=127 but map[0] implies 126 (writeIdTimes31=127)`.
- **Test:** the same, `HostTests.HandshakeStress_NoTearNoLoss` (run
  `35051069155`).
- **Status: open, and not the Group A defect.** `processor.h` has been unchanged
  since 2026-08-16 and `host_tests.cpp` since 08-17, so this tear survived the
  triple-buffer fix by a month. It is either a residual tear the triple buffer
  does not close, or a defect in the test's own invariant.
