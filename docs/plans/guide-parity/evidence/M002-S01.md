## M002/S01 — task 1: the weight mechanism and the timeline source

- `format` → exit 0
- `unit` → exit 0, 651 tests, 0 failures
- `engine-isolation` → exit 0, 528 tests, 0 failures

Written test-first; the cases failed to compile because neither `StepWeights`
nor the settings existed.

**A test that asserted the wrong unit's responsibility.**
`RefusesAnUnusableReference` originally expected `computeStepWeights` to refuse
an out-of-range lane index. It cannot: it receives an **already-resolved**
pattern, so the only bad references it can see are a negative index and a
self-reference. Whether lane N exists, and whether it points back, is the
resolver's question — which is what `referenceLaneUsable` exists for. The test
is now split along that line, and the split is the honest one rather than a
loosened assertion.

| Case | Guards |
|---|---|
| neutral with no reference lane | the byte-identity guarantee, as arithmetic rather than a promise |
| positive strength attracts adds | the mechanism does something |
| **negative strength inverts it** | that the *sign* is read — without this, an implementation reading only the magnitude would pass |
| drop moves opposite to add | protecting what attraction favours, the row's stated behaviour |
| refuses what it can see | self-reference and negative index |
| `referenceLaneUsable` refuses out-of-range, self and mutual | the resolver's half, mirroring kotekan's guard |
| refuses a step outside the cycle | that a bad index is not read out of bounds |

**The design's size claim, measured.** `GrooveState` grows 18000 → 18064,
**+64 bytes** — 8 per lane for an `int` and a `float`. The alternative the
issues proposed, four 64-float arrays per lane, would have been roughly 8 KB on
a struct copied three times per block. The three-copy pipeline measures
**0.46 µs/block, 0.02% of a 128-sample block period**.

## M002/S01 — task 2: the rolls read the weights

- `format` → exit 0
- `unit` → exit 0, 655 tests, 0 failures
- `engine-isolation` → exit 0, 532 tests, 0 failures
- `rt-safety` → exit 0

The weights scale the **thresholds**, never the roll. Perturbing the random
value would break the determinism the engine's contract rests on; moving the
threshold leaves `(patch, seed, transport)` determining the output exactly.

**A subtlety worth recording, because the code does not show it.** `typeRoll`'s
thresholds are cumulative — drop, then ghost, then add — so scaling the drop
edge moves where the ghost band begins, and the add band absorbs whatever the
two below it leave. Weighting the drop edge *down* therefore widens the add
band, which is precisely the intent: a timeline-aligned step is protected from
drops and more available for adds. One weight, two effects, both wanted.

Measured as distributions over 400 seeds rather than single rolls — one roll
says nothing about a probability.

**A false green, caught.** The first probe edit did not compile, and `ctest`
then ran the *previous* binary and reported all four cases passing. That is the
stale-build hazard `M002-decisions.md` carries a standing instruction about,
arriving in its most dangerous form: a probe that appears to prove the tests
cannot fail. The probe was redone as a compiling edit, with the build's success
checked before any result was read.

| Case | Under the probe (`hasTimeline` forced false) |
|---|---|
| positive strength shifts onsets toward the timeline | **fails** |
| negative strength shifts them away | **fails** |
| an unweighted lane is unchanged | passes |
| every factory preset unmoved | passes |

The two that survive are the ones about the *unweighted* path, so they cannot
distinguish weighted from unweighted — which is exactly why the first two carry
the claim.
