## [0.2.0] - unreleased

### Fixed

- **The release now knows what version it is, tests what it ships, and publishes something a downloader can verify.** Milestone M001 of the open-source-launch programme closes five rows in two slices. Five version strings had disagreed, and the one a DAW displayed was the wrong one: `plugids.h` hand-typed `1.0.0` while CMake built `0.1.0`, the two private npm manifests carried numbers nobody published, and the built bundle's own `moduleinfo.json` showed the module at one version beside both classes at another. The version is now typed once, in `project(poly VERSION 0.2.0)`: the SDK's `smtg_target_configure_version_file` generates `projectversion.h` and `plugids.h` reads `FULL_VERSION_STR` from it — called from the top-level list file, because the helper writes into the current binary directory but adds `PROJECT_BINARY_DIR` to the includes, and the three test targets that compile plugin sources directly needed that directory too. Proved by reading the bundle: at 0.2.0 all three values read 0.2.0, at a 0.2.1 mutation all three followed, and at 0.2.0 restored all three returned. `scripts/check-version-source.mjs`, wired into `guards`, fails if a literal returns or a manifest grows a version; it was red on the old tree, three of four cases, before being trusted. **The first version is 0.2.0**, by the owner's decision, and June's `0.1.0` section stays as history; `[Unreleased]` is now `## [0.2.0] - unreleased`, to be dated when the tag is cut, and the release-workflow contract asks `gen-release-notes.mjs` for the version `CMakeLists.txt` declares on every `guards` run, so a version bump without a changelog section fails locally rather than at tag time. **`release.yml` never ran `ctest`**, and the macOS universal binary is built nowhere else, so the one configuration a stranger downloads was the one whose tests never ran; a `Run tests` step now sits between Build and pluginval on both legs. **A Release published nothing to verify the zips against**; the release job now writes `SHA256SUMS` and attests build provenance per zip with `actions/attest-build-provenance` pinned by SHA, holding exactly the `contents`, `id-token` and `attestations` grants the action needs — the contract test asserts that set and nothing else. **pluginval was fetched and executed unverified at four sites** while every action in the tree is SHA-pinned; each site now pipes the v1.0.4 asset's SHA-256 through `shasum -a 256 -c` before unzip, and the contract test requires exactly four sites and the pinned digests. - **Every guard CI enforces can now be run locally, and the pre-push gate runs all of them that can run at all.** Milestone M007 of the engine-capability programme closes three ledger rows across three slices. Eleven checks ran in CI and from no command a developer could invoke — six shell guards (SPDX headers, personal paths, the site and scripts READMEs, the sample manifest, site assets) and five node checks (bridge schema coverage plus four green/red contract proofs) — so a complete local validation set could go green while CI failed on any of them, which is exactly what happened on three consecutive ships: M005 on `doc-drift`, M006 on `check-scripts-readme`, M002 on the params-json emitter. `scripts/check-guards.sh` now runs all of them under one declared `guards` token, deliberately without `set -e` so three simultaneous breaks report three named failures rather than one per invocation. **The reachability check written to close the class found a twelfth guard on its first run, worse off than the eleven:** `scripts/check-release-workflow.mjs` — 27 tests locking the release workflow's shape, that no Linux plugin zip is produced, that the validator flag stays on, the build → validate → pluginval → sign → package order — is named in `release.yml` only in comments and was executed by **nothing at all**. The eleven at least ran in CI. Two checks now stop the class recurring rather than the instances: a guard reachable from no declared token, the pre-push gate, `pre-commit`, or the doc-conformance runner fails, unless it carries an in-band `# local-unrunnable: <reason>` marker; and a validation token that is neither run by the pre-push gate nor declared exempt with a reason fails too. Both reject an empty reason, because a hatch that can be left blank silences the check instead of declaring an exemption. The gate itself went from seven steps to ten, gaining `site-unit`, `doc-discipline` and `guards` — measured at under a second, under a second, and five seconds, against a hook that already compiles the plugin and runs pluginval, for eighteen seconds end to end. That measurement reversed a decision this milestone had recorded earlier, that the guards should be runnable but not automatic on the grounds that not every push should pay for them; the ledger's decisions file keeps both entries in order, because the premise was wrong rather than the reasoning. `CLAUDE.md` asserted the hook covered "the five items above and nothing else, by design" while the script had seven steps — a rule living only in a document and not being followed, which is this programme's recurring defect in miniature — and now carries a table of what actually runs plus the rule behind it: the local gate is CI minus what genuinely cannot run locally, with each of the five exclusions declared beside its token. The site suite gained the two cases that enforce this, and stands at 285. (engine-capability M007)

- **The doc gate could not be run locally, so `doc-drift` was enforced in CI and nowhere else.** `jk-standards all` skips `doc-drift` whenever no base ref is available, printing `doc-drift: no --base or GITHUB_BASE_REF — skipped` and exiting 0 — which in a wall of green output reads like a pass. CI supplies `GITHUB_BASE_REF` and therefore ran the check; a developer running the `doc-discipline` validation token did not, and had no way to tell. M005 shipped a doc-drift violation through a validation set that was green on every other count, and M001 satisfied the same drift rule only incidentally, having touched `docs/preset-taxonomy.md` because adding presets forced the count updates — so that rule had been locally unenforced for the whole programme. `scripts/check-doc-discipline.sh` now supplies the base CI supplies, the `doc-discipline` token points at it, and `CLAUDE.md` says plainly that the pre-push hook does not cover the doc checks and names the command that does. Where no base is determinable at all — a detached HEAD, a shallow clone — it explains that in plain words and runs the remaining checks rather than failing, because explaining is not the same as skipping in silence. All three paths were proved: a real drift violation fails naming the mapping, an unresolvable base fails loudly with jk-standards' own `cannot resolve base ref`, and the no-base path prints its explanation and continues. (M006 S01)

- **Seven of the twenty-three `site/tests` files ran in no CI job at all.** The only files CI executed were the sixteen named in `scripts/check-doc-conformance.sh`; nothing ran `npm --prefix site test`, so `bjorklund`, `doc-conformance-wiring`, `dump-mode`, `preset-patterns`, `presets-json-schema`, `sample-loader` and `smf-writer` were proven only on whoever's machine last ran them. That included the guard M005 had just added to catch a stale `presets.json` — the check against a silent correctness bug was itself unproven. The `site-lint` job now runs the whole suite, which needs no per-file wiring because the script is a directory glob, so a new test file is picked up automatically and the orphan case stops existing. A case in `doc-conformance-wiring.test.mjs` asserts the CI step is still there, and that file was added to the conformance runner so the guard is not executed solely by the step it guards. This closes [#272](https://github.com/JimAKennedy/poly/issues/272), whose count of seven was right — only its total of twenty-one had drifted. (M006 S02)

- **The preset generator trusted a stale binary, so a change to the engine could silently produce the previous engine's `presets.json`.** `ensureEmitter()` in `site/scripts/generate-presets-json.mjs` returned as soon as the emitter binary existed and rebuilt it only when missing — so editing `engine/src/presets.cpp` left the old binary in place and the generator emitted last build's data while reporting success. The file's own header calls a stale `presets.json` "a silent correctness bug we already paid for", and M001/S02 paid it again, writing 43 presets after the engine had 44. The early return is gone: cmake is already incremental, so building every time costs a no-op on an unchanged tree, which is cheaper and more honest than any mtime comparison this script could implement correctly against C++ sources. Reproduced before being fixed — with one preset's kick velocity changed and no explicit build, the generator reported success and the JSON kept the old value; afterwards the same run rebuilt and the new value appeared. The clean-tree path was re-proved rather than assumed, since removing an early return is exactly the change that could break it. Separately, the schema test's expected preset count is no longer a literal that had to be hand-edited once per preset added: it is read from `kFactoryPresetCount` in `engine/include/poly/presets.h`, so the engine and the generated file disagreeing is a test failure. That guard was proved twice — a wrong count fails naming both numbers, and a *renamed* constant fails loudly rather than matching nothing, which is the vacuity `CLAUDE.md` records this repo shipping once before. (M005 S01)

- **`Cuban Son Montuno` played `E(5,16)`, not the son clave — the two differ by one pulse, and the guide had been documenting that difference while the preset shipped the wrong side of it.** The clave lane carried no hand-authored pattern, so `lockPresetReferent` baked the Euclidean distribution of its hit count and cycle into the timeline slots: onsets `{0, 3, 6, 9, 12}` against the son clave's `{0, 3, 6, 10, 12}`. That is the displacement at the ponche which Chapter 3 describes, and `theory-afro-cuban.mdx` had been telling readers to build a true clave by hand in timeline mode precisely because no shipped preset had one. The pattern is now authored in `makeCubanSon`, which also stops `lockPresetReferent` re-baking it — the mechanism by which the four existing hand-authored timelines survive. One engine invariant was incomplete and was corrected alongside it: `isReferentLocked` required every perturbation neutralised "so no runtime input can move the reference" but never checked `driftRate`, which rotates which step sounds on every bar; `lockPresetReferent` already skipped phasing lanes when *choosing* a referent, so only the predicate deciding whether a lane *is* one omitted it. Across all 45 presets exactly one timeline lane drifts, so no other preset's referent count moves. (M001 S02)

- **The Cubase nightly runs unattended again: the L4-web CDP e2e no longer needs a human to launch Cubase.** Root cause of the M042 S09 dead end (runs #40–#47, where 0 of 18 `msedgewebview2.exe` children ever carried `--remote-debugging-port` while a hand-launched Cubase exposed it every time) was that the runner's `GitHubActionsRunner` logon task ran with `-RunLevel Highest`, so Cubase inherited high integrity — and [WebView2 discards browser flags delivered via the environment or the registry for elevated host apps by design](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/webview-features-flags). Passing the flag "via code" instead is documented to survive elevation but is blocked by an open regression making the DevTools endpoint unreachable for elevated hosts on WebView2 Runtime ≥ 150 ([WebView2Feedback#5640](https://github.com/MicrosoftEdge/WebView2Feedback/issues/5640); the runner is on 151.x), so a non-elevated Cubase is the only supported configuration. The runner task is now registered `-RunLevel Limited`, the workflow installs the plugin to the per-user VST3 folder (`%LOCALAPPDATA%\Programs\Common\VST3`) that a non-admin can write, the `schedule:` trigger and automated launch are restored, and the `manual_cubase` dispatch input plus the `await-manual-cubase.ps1` operator gate are gone. `launch-cubase.ps1 -EnableCdp` and `launch-manual-cdp.ps1` now refuse to run elevated, the install step fails the job on a stale machine-wide bundle shadowing the fresh one, and `diagnose-editor-window.ps1` records process elevation in `editor-window-topology.txt`. (M042 S09)

### Changed

- **The twelve theory deep dives no longer ship, and every guard that asserts their content still runs.** Milestone M002 of the first-release programme closes eleven rows. The pages move to `site/src/content/theory/` rather than being deleted, because they are deferred for a later release rather than retired — and the destination is decided by their imports, not by preference: every deep dive opens with `'../../components/PolyPatch.astro'`, which resolves to the same file from a sibling under `site/src/content/` and to a nonexistent root-level `components/` from anywhere else, so the imports are byte-identical and republishing is a config change rather than an edit to twelve files. `site/src/content.config.ts` defines only the `docs` collection, so the build emits **35 pages and zero theory routes**, verified by inspecting `site/dist` rather than by the absence of an error. The site stops pointing at them first and the pages move second — the reverse order would have left a commit with twelve callouts and a nav group aimed at routes that no longer existed. **Sixteen documents linked in, not the twelve the plan counted**, in two forms: nine markdown links and five plain-prose rule citations of the shape `(theory-minimalism Rule 6)`, which have no link to break and so would never have 404'd while still naming a section a reader cannot reach. The deferred bundle carries its own bibliography, `theory-references.mdx`, holding the **93 anchors** the deep dives cite — 66 exclusively theirs — derived from the pages rather than curated, because a missed anchor is a citation that dangles the day they are published again and nothing would warn in the meantime, `research_provenance`'s roots having stopped at the published docs. That scoping is now commented in `jk-standards.yaml` at both roots, so a later widening is a deliberate act rather than a silent one. Each deep dive that has one also gained a **"Presets that bend these rules"** section naming the factory presets that knowingly break its rules and which rule each breaks — the relationship the removal would otherwise have destroyed, recorded from the rules' side where it cannot rot, with the preset-to-rule pairs recovered from git rather than recalled and every name checked against `presets.json`. **The spec suite was the authoritative enumeration, not grep:** the plan named ten test files needing repointing, six did, and they were not the six a grep would have found — four read shipping chapters and deep dives in the same test, so a blanket path swap would have broken them, and one never appeared in any `ENOENT` because its claim helper reports a missing file as a failed claim. 327 tests pass against 324 before the milestone. (first-release M002)

- **Poly's supported plugin targets are now explicitly macOS and Windows; Linux is engine/WASM only.** M054 decision D029 (Path 3) settled the long-standing "what does the Ubuntu build mean" question: Poly ships no Linux VST3 binary, so the ubuntu-latest CI leg was flipped to an engine-only portability compile (`-DPOLY_ENGINE_ONLY=ON`) and the `pluginval-linux` job (which was validating a full-but-editorless Linux plugin that ships to nobody) was deleted along with its `ci-complete` aggregation-gate references. The `plugin/CMakeLists.txt` WebUI block stays gated on `if(APPLE OR WIN32)` — there is no plan to wire up choc's WebKitGTK backend. No behavior changes for macOS/Windows users or for the engine/WASM build; developers rebuilding on Linux get a fast engine compile with no VST3 SDK or UI dependencies. (M054 S02)
- **Factory presets were conformed for musical accuracy and their downstream artefacts regenerated to match.** The engine preset definitions in `engine/src/presets.cpp` were edited across S01–S04: the Kotekan Interlock polos was thinned to E(2,3) (hits 3→2) with its emphasis probability re-baked to 1.0, the Agbekor support drums were de-saturated, and neutralized default macros were removed. The engine-emitted `site/src/generated/presets.json` and the committed Try-It WASM engine (`webui/poly_engine.{wasm,js}`, which compiles `presets.cpp` in) were regenerated from the conformed engine in one reviewed pass so the site's Play card and Try-It agree on every edited preset (Balinese Kotekan, Tintal Groove, Rupak Tal, Minimal Techno, Classic Funk, Jungle Break, Liquid Drum and Bass, Afro-Electronic Fusion, Balkan Funk). The determinism golden fixtures use a synthetic patch independent of factory presets and were re-verified byte-identical, not regenerated. (M070)
- **The Euclidean onset generator is now Bjorklund's algorithm everywhere — engine, WASM, and site — replacing the engine's prior Bresenham distribution.** `engine/src/euclidean.cpp` now computes onsets with an RT-safe Bjorklund implementation that matches Toussaint's documented spellings (E(3,8), E(5,8), E(5,16), E(3,7), E(4,9), E(7,12)), and the site's diagram and Try-It playback now import one shared `site/src/audio/bjorklund.ts` so the browser cannot fork from the engine. The Try-It WASM engine (`webui/poly_engine.{wasm,js}`) and the engine-emitted `presets.json` were regenerated against the new generator, and the golden determinism fixtures were re-verified against it (they were already consistent). **Migration is lossless:** `kStateVersion` was bumped to 16 and a per-lane rotation is applied on load so any pre-switch (v15) saved state re-derives its original per-lane onsets under the new Bjorklund spelling — existing projects sound identical after the upgrade. (M068)
- **WebUI Timeline mode toggle now seeds the step pattern from the lane's current Euclidean configuration** (steps × hits × rotation) instead of starting empty. Enables the Euclidean-approximation-then-manual-refinement workflow: set steps/hits/rotation to get a close Euclidean starter (e.g. E(5,16) for son clave), flip Timeline mode to inherit those hits as an editable step grid, then shift one or two steps to reach the exact traditional pattern. ## [0.1.0] - 2026-06-27

Initial open-source release of Poly, a polymetric drum pattern generator outputting MIDI via VST3.

### Added

#### Engine
- Euclidean rhythm generator with 4–8 independent lanes, each with configurable steps, pulses, and rotation
- Additive/aksak cell support for variable-width Euclidean rhythms (e.g. 2+2+3)
- Dynamic shaping: accent masks, emphasis probability, and ghost note floor per lane
- Envelope superposition system with 8 targets (velocity, density, pulse count, rotation, accent, ghost, swing, humanize), supporting Curve and StepList shapes
- Constraint layer: anchors, backbeat protection, and density guardrails
- A/B scene system with morph interpolation for live parameter blending
- Macro controls: complexity, density, syncopation, swing, tension, humanize — with transition smoothing
- Per-lane swing, humanize, and note duration controls
- Phrase gating with per-lane length/gap/offset controls in beats
- Per-lane pattern mutation with deterministic per-cycle variations
- Per-lane phase drift with deterministic PPQ-based rotation
- Kotekan pair mode and timing offset knob
- Per-step micro-timing maps for groove templates
- Timeline mode for fixed-pattern lanes immune to macro changes
- Deterministic output: same (patch, seed, transport) inputs produce identical MIDI every time

- VST3 instrument with 16-channel MIDI output via IEventList
- Full Cubase automation: VST3 unit hierarchy, parameter formatting, clean naming
